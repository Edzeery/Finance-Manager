## 2. Items Confirmed Still Open

### 2.1 — `PaymentFailed` event has no listeners (unchanged from prior audit)
`App\Events\PaymentFailed` is dispatched three times from `app/Services/Payments/Chargily/ChargilyWebhookService.php:193,220,247` via `Event::dispatch(new PaymentFailed(...))`. No `Event::listen(PaymentFailed::class, ...)` registration exists anywhere in the codebase. These dispatches are currently no-ops — any intended side effect (admin alert, retry scheduling, customer notification) never fires.

Note: this is distinct from `App\Mail\PaymentFailed`, a **Mailable** (not an Event) that *is* correctly queued from `app/Services/PaymentService.php:294` on manually-rejected payments. Only the Chargily-webhook Event path is orphaned.

### 2.2 — Webhook DB audit logging (`payment_webhook_logs`) is Chargily-only
Confirmed by direct inspection of `app/Http/Controllers/PaymentWebhookController.php`:
- `paypal()` (line 90), `stripe()` (line 125), `wise()` (line 160), `payoneer()` (line 206), `noest()` (line 239) all call `$this->logWebhookEvent(...)`, which (lines 186-197) does **only** `Log::info('Webhook received', $safeContext)` — a text log line, not a DB record.
- Only `ChargilyWebhookService.php:85-91,263-268` writes to `PaymentWebhookLog::create()` / `::update()`.

Five of six webhook-receiving gateways (PayPal, Stripe, Wise, Payoneer, Noest) have no queryable, admin-visible audit trail for disputes or debugging — only ephemeral application logs.

### 2.3 — Raw string status values still used instead of `PaymentVerificationStatus` enum
`PaymentService::verifyPayment()` (`app/Services/PaymentService.php:190`) and `applyPaymentSideEffects()` (`:227`) both type their `$status` parameter as plain `string`, not `PaymentVerificationStatus`. Raw literals `'approved'` / `'rejected'` are compared/passed at:
- `app/Services/PaymentService.php:204, 235, 283`
- `app/Http/Controllers/PaymentReturnController.php:58`
- `app/Http/Controllers/SuperAdmin/PaymentController.php:135, 215`
- `app/Http/Controllers/PaymentWebhookController.php:59, 68` (all five webhook handlers route through these two private methods)
- `app/Console/Commands/CheckNoestDeliveries.php:35`

The enum (`app/Enums/PaymentVerificationStatus.php`) exists and is correctly used for the `PaymentVerification::status` cast, but the service-layer API contract never enforces it — a typo (`'aproved'`) would silently fail every comparison with no static or runtime error.

### 2.4 — `CreateAdminNotification` listener is dead code (escalated finding — more severe than previously documented)
Prior audits flagged this as "duplicate `LogAuthEvent` registration between `EventServiceProvider` and `AppServiceProvider`." Re-investigation shows the actual defect is worse:

- `app/Providers/EventServiceProvider.php` exists and defines six `Event::listen()` bindings (`PaymentCompleted` → `SendPaymentReceipt`, `ActivateWorkspace`, `CompleteOnboarding`, `CreateAdminNotification`; `SubscriptionActivated` → `CreateAdminNotification`; `Registered` → `CreateAdminNotification`) plus `Event::subscribe(LogAuthEvent::class)`.
- **This provider is not registered anywhere.** `bootstrap/providers.php` lists only: `AppServiceProvider`, `VoltServiceProvider`, `SettingsServiceProvider`, `BindingServiceProvider`, `GatewayServiceProvider`, `RateLimiterServiceProvider`, `ModelEventServiceProvider`, `PolicyServiceProvider`, `LivewireServiceProvider`, `Volt\VoltServiceProvider`. `EventServiceProvider` is absent, and `bootstrap/app.php` has no `->withEvents()` call referencing it either. The entire file is dead code — none of its `boot()` logic ever executes.
- `LogAuthEvent` still works only because it is *separately, correctly* registered in `app/Providers/AppServiceProvider.php:34` (`Event::subscribe(LogAuthEvent::class)`). This is not a harmful duplicate — it's the only registration that actually runs.
- `ActivateWorkspace`, `CompleteOnboarding`, and `SendPaymentReceipt` all type-hint a specific event class in their `handle()` signature (e.g. `handle(PaymentCompleted $event)`), so Laravel 11+/13's automatic event discovery (which scans `app/Listeners` independent of `EventServiceProvider`) picks them up regardless. These three are very likely still functioning.
- **`CreateAdminNotification::handle(object $event)`** (`app/Listeners/CreateAdminNotification.php:17`) type-hints the generic `object`, not a specific event class. Laravel's auto-discovery requires a concrete event type on the first parameter to bind a listener — a generic `object` hint is not discovered. Combined with the orphaned `EventServiceProvider`, **this listener is never invoked by any mechanism**. Admin notifications for completed payments, activated subscriptions, and new registrations (`handlePayment()` at line 35, `handleSubscription()` at line 45, plus whatever branch handles `Registered`) are silently non-functional.

This should be treated as **critical**, not medium — it affects operational visibility into every payment and subscription event, not just a cosmetic duplication.

## 3. Confirmed Architectural Decision (New)

**Per-currency independent yearly pricing is intentional, not a regression.**

`database/migrations/2026_07_07_000003_create_plan_features_and_prices_tables.php` introduces a `plan_prices` table (`plan_id`, `billing_period`, `currency`, `price`, `is_active`, unique on `[plan_id, billing_period, currency]`), backed by `app/Models/PlanPrice.php`. `SubscriptionPlan::getYearlyPriceAttribute()` (`app/Models/SubscriptionPlan.php:129-138`) now resolves price in this order:
1. `PlanPrice` row for `billing_period = 'yearly'` if one exists for the plan (allows a currency-specific, independently-set yearly price).
2. Fallback: `monthly_price × 12 × (1 − yearly_discount_percent / 100)` — the original formula, preserved as a fallback only.

**This supersedes the prior standing decision** ("no independently stored yearly values permitted; yearly price must always be computed from `monthly_price × 12 × (1 − discount/100)`"). The user has confirmed (2026-08-08) this is a deliberate move toward multi-currency pricing support, since a single discount-percentage formula does not hold consistently across currencies with independent rounding/market pricing. **This document supersedes the earlier decision on this point going forward.**

Action item: update `SUBSCRIPTIONS.md` and `DATABASE_SCHEMA.md` to reflect the `plan_prices` table and the new precedence rule (explicit price wins over formula).
